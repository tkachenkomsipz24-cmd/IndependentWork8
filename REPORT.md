## 1. Результати аналізу open-source прикладів

### Приклад 1 — `Dictionary<Type, DbType>` у Dapper

- **Проєкт / файл:** [Dapper, `SqlMapper.cs`](https://github.com/StackExchange/Dapper/blob/684d7d9895e8b9eff4ab898528d69bd60979c098/Dapper/SqlMapper.cs)
- **Колекція:** `private static Dictionary<Type, DbType> typeMap` — заповнюється в статичному конструкторі `SqlMapper` (`[typeof(int)] = DbType.Int32`, `[typeof(string)] = DbType.String` тощо).
- **Контекст:** Dapper має перетворити тип .NET параметра запиту на тип ADO.NET (`DbType`). Пошук виконується для кожного параметра кожного запиту.
- **Чому Dictionary, а не List/Array:** відповідність «тип → тип БД» — це пошук за ключем. У `List<KeyValuePair>` довелося б перебирати всі пари (O(n)), у словнику пошук O(1).
- **Складність:** пошук `TryGetValue` — O(1) у середньому; заповнення відбувається один раз при старті.
- **Особливі вимоги:** окремий comparer не потрібен — для `Type` достатньо стандартного порівняння за посиланням. Словник наповнюється один раз і далі лише читається, тому для нього не потрібна синхронізація потоків (на відміну від `_queryCache` у тому ж файлі, де Dapper використовує потокобезпечний словник, бо кеш змінюється під час роботи).

### Приклад 2 — `Dictionary<StructMultiKey<Type, Type>, JsonContract>` у Newtonsoft.Json

- **Проєкт / файл:** [Newtonsoft.Json, `CamelCasePropertyNamesContractResolver.cs`](https://github.com/JamesNK/Newtonsoft.Json/blob/master/Src/Newtonsoft.Json/Serialization/CamelCasePropertyNamesContractResolver.cs)
- **Колекція:** статичне поле `Dictionary<StructMultiKey<Type, Type>, JsonContract>? _contractCache`.
- **Контекст:** створення `JsonContract` (опис того, як серіалізувати тип) — дорога операція з рефлексією, тому результат кешується для пари «тип resolver-а + тип об'єкта».
- **Чому Dictionary:** кеш за ключем — головний сценарій використання словника: знайти вже обчислене значення за O(1) замість повторного створення.
- **Складність:** пошук O(1) у середньому. Створення контракту (рефлексія) значно дорожче за пошук у кеші, тому кеш окупається.
- **Особливі вимоги:** складений ключ із двох типів; потокобезпека досягається підходом copy-on-write — при додаванні елемента під `lock` створюється нова копія словника, а старий не змінюється. За коментарем у коді, це робиться, щоб не змінювати словник, поки інший потік його читає.

### Приклад 3 — `HashSet<string>` у `PropertyIgnoreSerializerContractResolver` (розширення Newtonsoft.Json)

- **Джерело:** [GitHub Gist: PropertyIgnoreSerializerContractResolver](https://gist.github.com/arman-hpp/137057680049be36afcee95b7c02af65) (код користувача, який розширює `DefaultContractResolver` з Newtonsoft.Json).
- **Колекція:** `private readonly HashSet<string> _ignores`; перевірка `_ignores.Contains(jsonPropertyName)` у методі `IsIgnored`.
- **Контекст:** під час серіалізації потрібно швидко визначити, чи входить властивість у список тих, що слід пропустити.
- **Чому HashSet:** потрібна лише відповідь «є / немає» без значень; множина сама відкидає дублікати імен. `List<string>.Contains` перебирав би всі елементи (O(n)) для кожної властивості кожного об'єкта.
- **Складність:** `Add` і `Contains` — O(1) у середньому.
- **Особливі вимоги:** порядок не важливий; для імен властивостей можна передати `StringComparer.OrdinalIgnoreCase`, якщо регістр не має значення.

### Приклад 4 — `HashSet<Type>` у `SolrContractResolver`

- **Джерело:** [GitHub Gist: SolrContractResolver](https://gist.github.com/anonymous/82055eb397fc65068f9987df7160df0a).
- **Колекція:** `HashSet<Type> typesNotRequiredToConvert` — набір простих типів, які Solr підтримує без спеціального перетворення.
- **Контекст:** для кожної властивості перевіряється, чи потрібне перетворення значення в JSON-рядок.
- **Чому HashSet:** це перелік унікальних типів і єдина операція над ним — перевірка належності.
- **Складність:** `Contains` — O(1).

### Додатково: обидві колекції разом — `Dictionary<Type, HashSet<string>>`

- **Джерело:** [GitHub Gist: PropertyFilterResolver](https://Gist.github.com/weitzhandler/9dd5575bea2393a8bff3165a0c73a8eb).
- **Колекція:** `Dictionary<Type, HashSet<string>> Map` — для кожного типу зберігається множина імен властивостей, які треба включити або виключити.
- **Чому саме так:** словник знаходить множину за типом за O(1), а `HashSet` гарантує унікальність імен і швидку перевірку належності. Така ж структура використана в сценарії 3 (`SearchIndex`) моєї програми.

> Примітка: приклади 3–5 — це відкритий код зі спільноти (Gist), що будується навколо Newtonsoft.Json, а не код ядра самої бібліотеки.

## 2. Порівняльна таблиця

| Операція | `List<T>` | `Dictionary<TKey, TValue>` | `HashSet<T>` | Коли використовувати |
|----------|-----------|----------------------------|--------------|----------------------|
| Додавання | O(1) в кінець (амортизовано); O(n) у середину | O(1) у середньому | O(1) у середньому | List — коли важливий порядок; Dictionary/HashSet — коли важливий швидкий доступ |
| Пошук за значенням | O(n) | O(n) (перебір значень) | N/A | Якщо часто шукаєте за значенням — потрібна інша структура |
| Пошук за ключем | N/A (лише за індексом O(1)) | O(1) у середньому | N/A | Dictionary — кеші, довідники, індекси |
| Видалення | O(n) | O(1) у середньому | O(1) у середньому | Dictionary/HashSet значно швидші на великих обсягах |
| Перевірка наявності | O(n) (`Contains`) | O(1) (`ContainsKey`) | O(1) (`Contains`) | HashSet — коли потрібні лише «є / немає» |
| Унікальність | Ні | Ключі унікальні | Елементи унікальні | HashSet — для унікальних значень |
| Порядок елементів | Зберігається | Не гарантується | Не гарантується | List — для впорядкованих даних |
| Операції над множинами | Немає | Немає | `UnionWith`, `IntersectWith`, `ExceptWith` | HashSet — для об'єднання, перетину, різниці |

O(1) для `Dictionary` та `HashSet` — середній випадок. У найгіршому випадку (багато колізій через поганий `GetHashCode`) операції можуть деградувати до O(n).

## 3. Висновки про вибір колекції

**Коли `Dictionary` кращий за `List`.** Коли дані потрібно знаходити за ключем (шлях файлу, тип, id), а не за позицією. `List` змусив би перебирати елементи, а `Dictionary` знаходить значення за O(1). Це підтверджують приклади Dapper (`typeMap`) та Newtonsoft.Json (`_contractCache`), а також `FileMetadataCache` у моїй програмі.

**Коли `HashSet` оптимальний.** Коли потрібні лише унікальність і швидка перевірка належності (множина ігнорованих властивостей, теги статті, id документів), а також операції над множинами (об'єднання, перетин, різниця): `GetAllUniqueTags`, `FindCommonTags`, `SearchMultiple`.

**Підводні камені:**

- Ключі й елементи мають коректно реалізовані `Equals` та `GetHashCode`: рівні об'єкти повинні мати однаковий хеш-код. Для власних класів без цього `Dictionary` і `HashSet` порівнюють за посиланням.
- Не можна змінювати поля, від яких залежить хеш-код, поки об'єкт лежить у колекції: його не вдасться знайти.
- Порядок елементів не гарантується.
- `Dictionary` та `HashSet` не потокобезпечні: для багатопотокового кешу потрібні `ConcurrentDictionary`, блокування або copy-on-write, як у Newtonsoft.Json.
- Поганий `GetHashCode` дає багато колізій і руйнує продуктивність (деградація до O(n)).
- Для рядків слід свідомо вибирати comparer (`StringComparer.OrdinalIgnoreCase` тощо), інакше «Hello» і «HELLO» вважатимуться різними.

## 4. Відповіді на контрольні питання

1. **Переваги generic-колекцій.** Типобезпека на етапі компіляції, відсутність боксингу значущих типів і приведень типів, краща продуктивність, повторне використання одного коду для будь-яких типів.
2. **Де використовувати `Dictionary<TKey, TValue>` та `HashSet<T>`.** `Dictionary` — для пошуку значення за ключем: кеші, довідники, індекси, групування. `HashSet` — коли потрібні унікальні елементи, швидка перевірка наявності та операції над множинами (теги, фільтри, чорні списки).
3. **Вплив `IEqualityComparer<T>`.** Визначає, коли два ключі/елементи вважаються однаковими (коректність) і як розподіляються хеш-коди (продуктивність). Без нього для класів порівнюються посилання, для рядків — з урахуванням регістру. Приклади: `StringComparer.OrdinalIgnoreCase` для `Dictionary<string, int>` та `PersonNameComparer` для `HashSet<Person>`. Умова: `Equals` і `GetHashCode` мають бути узгодженими.
4. **Чому інвертований індекс будують на `Dictionary<string, HashSet<int>>`.** Словник за O(1) знаходить множину документів за словом. `HashSet<int>` гарантує, що документ для слова зберігається один раз, і дає швидкий перетин для пошуку за кількома словами (`IntersectWith`) та об'єднання для пошуку за будь-яким зі слів (`UnionWith`).
